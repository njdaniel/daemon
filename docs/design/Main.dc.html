How would you design a rate limiter for a globally distributed API?

Focus: architecture, consistency tradeoffs, Redis/distributed state, failure handling.

APPROACH llama3.1:8b · 1.2s
  1. 1Clarify requirements and rate-limit scope.
  2. 2Use token bucket or sliding-window counters.
  3. 3Store counters close to request processing.
  4. 4Discuss Redis/local caches and global consistency.
  5. 5Cover failure modes and observability.

Algorithm. Token bucket per key (user/API key/IP). Sliding-window log is exact but memory-heavy; sliding-window counter is the usual middle ground.

Placement. Enforce at the edge/gateway. Counters in a regional Redis cluster; local in-process cache absorbs bursts before hitting Redis.

Global. Don't demand strong consistency. Per-region quotas with async reconciliation; accept small over-admission.

Failure. Redis down → fail open with a conservative local limit, alert. Return 429 with Retry-After and X-RateLimit-* headers.
  • What happens when a client hits the limit in two regions at once?
  • How do you handle clock skew between nodes?
  • How would you rate-limit by cost instead of request count?
  • How do you roll out a limit change without breaking clients?
