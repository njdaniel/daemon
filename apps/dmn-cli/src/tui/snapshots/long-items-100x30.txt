┌ LIVE QUESTION ──────────────────────────────────────────────────────────────────── system design ┐
│ How would you design a rate limiter for a globally distributed API, and how would you handle the │
│ case where the limiter itself goes down?                                                         │
│ Focus: architecture, consistency tradeoffs, distributed state, failure handling                  │
│                                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
┌ APPROACH ────────────────────────────────────────────────────────────────────────────────────────┐
│ 1  Clarify scope: per user, per API key or per IP, and the limits per tier.                      │
│ 2  Use a token bucket per key; sliding-window counters if bursts matter.                         │
│ 3  Keep counters in regional Redis with a local in-process cache in front.                       │
│ 4  Accept small over-admission across regions; reconcile quotas asynchronously.                  │
│ 5  If Redis is down, fail open to a conservative local limit and alert.                          │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
  1 ▾ Deeper Answer
      Algorithm: Token bucket per key: refill r tokens a second up to burst b, and take one per
      request. It needs two numbers per key and one atomic update, where a sliding-window log
      keeps each timestamp and a fixed window lets a burst through at its edge.
      State: Keep the counters in a Redis cluster per region and update them in a Lua script, so
      the read and the write are one step. A tiny in-process cache in front absorbs hot keys and
      cuts the Redis round trips to one per key every few milliseconds.
      Consistency: Regions do not share counters on the request path. Each one enforces its share
      of the quota and reports usage to a reconciler, which moves any unused share to busy regions
      every few seconds, so a partition over-admits by one share at worst.
      Failure: If Redis is unreachable the limiter fails open to a conservative per-instance limit
      held in its own memory, sends an alert and marks its decisions as degraded in the access
      log, so abuse during the outage can be found and billed afterwards.
